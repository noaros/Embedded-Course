# Lab 10: Unbrickable update

**Board:** NUCLEO-H723ZG · **Time:** 2.5 h (plus an unattended power-cut run) · **Builds on:** Module 10, Module 2 (linker scripts), Module 8 (watchdog resets)

You complete a bootloader that accepts only signed images, keeps two application slots, boots a new image on trial, and reverts if it never confirms. Then you attack it with 50 power cuts at random points during updates. The device must come back up with a valid image every single time.

```
0x08000000  sector 0     bootloader (yours)
0x08020000  sectors 1-3  slot A: [1 KB signed header][app linked at 0x08020400]
0x08080000  sectors 4-6  slot B: [1 KB signed header][app linked at 0x08080400]
0x080E0000  sector 7     boot state: append-only 32-byte records
```

## Files

```
common/                 shared by starter and solution (complete)
  flash_layout.h image.h        layout, header format
  flash_h7.c/h                  sector erase, 32-byte flash-word programming
  boot_state.c/h                append-only boot record log with CRC
  boot.ld app_slot_A.ld app_slot_B.ld   linker scripts (include bsp/h723/h723_sections.ld)
  pubkey.h                      the signer's public key (generated by tools/fw_sign.py)
  lab10.cmake                   builds and signs everything
starter/boot/main.c     bootloader: TODO 1-4
starter/app/main.c      application: TODO 5-6
tools/fw_sign.py        keygen + signing
tools/fw_update.py      sends an image over UART
tools/powercut_test.py  the 50-cut torture test
tools/keys/             the DEMO signing key (see its README)
```

Build everything:

```sh
pip install cryptography pyserial
cmake --build build --target lab10_starter_boot lab10_starter_app_A lab10_starter_app_B lab10_starter_app_bad_B
```

The build signs each app automatically (`*.signed.bin` next to the ELF) when Python and `cryptography` are available. Version and counter come from CMake cache variables:

```sh
cmake -S . -B build -DLAB10_APP_VERSION=1.1.0 -DLAB10_APP_COUNTER=2
```

## What you hand in

1. Your bootloader and application changes (TODO 1–6).
2. Logs showing: first boot of slot A; an update to B (trial, confirm); the `bad_B` image reverting to A after 3 attempts; a **tampered** image (flip one byte of a signed `.bin`) being rejected; an **older counter** image being refused.
3. The power-cut run: `powercut_test.py` output for 50 rounds, with **50/50** booting a valid image, and a note on how you cut the power (a real power cut vs NRST reset).
4. Answers: (a) why does the bootloader append the attempt count *before* jumping? (b) why does the app, not the bootloader, raise the anti-rollback floor, and why only on confirm? (c) where is the remaining power-fail window in `boot_state.c`, and how would you close it?

## Steps

### 1. Bring-up (30 min)

1. **TODO 3 (jump).** Flash the bootloader ELF and `lab10_starter_app_A.signed.bin` at `0x08020000`:

   ```sh
   STM32_Programmer_CLI -c port=swd -d build/.../lab10_starter_boot.elf
   STM32_Programmer_CLI -c port=swd -d build/.../lab10_starter_app_A.signed.bin 0x08020000 -rst
   ```

   You should see the `BOOT:` lines, then `APP v1.0.0 ... slot A`.
2. **TODO 2 (watchdog) + TODO 5 (refresh).** With TODO 2 alone the app resets every 4 s. Explain why from the reset flags the bootloader prints. Then add TODO 5.

### 2. Authenticity (30 min)

3. **TODO 1 (verify).** First, prove the starter's check is worthless: flip one byte of the payload in a signed image, flash it to slot A, and watch it boot. Then implement the real check and repeat. The image is now rejected, and with no other valid image the bootloader sits in update mode.
4. Build an image with `-DLAB10_APP_COUNTER=0` after a counter-1 image has confirmed. It must be refused ("rollback refused").

### 3. Updates and trial boot (40 min)

5. **TODO 6 (confirm)** and **TODO 4 (trial boot).** Update to slot B over UART:

   ```sh
   python3 tools/fw_update.py /dev/ttyACM0 build/.../lab10_starter_app_B.signed.bin --request
   ```

   Expected: `slot B on trial, attempt 1 of 3` → `APP ... slot B` → `APP: confirmed`. Press `s` in a terminal to see the boot record.
6. Send `lab10_starter_app_bad_B.signed.bin` (it never confirms). Reset the board 3 times (or let your app's self-test fail): attempts 1, 2, 3, then the revert to slot A.

### 4. Power-cut torture (unattended, 30–60 min)

7. Run `tools/powercut_test.py` with 50 rounds, alternating between your A and B images. Read the script's header for how to cut power. A USB hub with per-port power switching (`uhubctl`) is the most realistic option on a desk.

   Any round that doesn't boot a valid image is a bug. Find it from the logs, fix it, and re-run all 50.

## Stretch goals

- **Close the log-erase window.** Use two sectors (6 and 7) for the boot state, ping-pong: write the first record of the new sector before erasing the old one. You'll have to shrink slot B.
- **ECC-safe state scan.** Cut power during `boot_state_append()` itself (add a delay before the program to widen the window). What happens when the bootloader reads a half-programmed flash word? Catch the double-ECC fault in a BusFault/NMI handler during the scan and skip the word.
- **Resume.** Make the update resumable after a cut: the bootloader reports the highest chunk it has, and `fw_update.py` continues from there.
- **MCUboot.** Port the application to MCUboot (Zephyr or the standalone port) in swap-move mode, and compare flash usage, update time and the number of erases per update.
